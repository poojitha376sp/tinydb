# ADR-011: Agents Run as an Unprivileged User, Checked with the Project's Own CI Tools (supersedes ADR-005)

## Status

Accepted. Supersedes ADR-005.

## Context

ADR-005 removed GitHub tokens from agents and gave each role a command allowlist. Building it showed three gaps:

- An allowlist alone does not stop an allowed program (for example `python`) from reading the runner's environment, which holds the job's token and the model keys, or files owned by the runner user.
- ADR-005 named `ruff` for the Stage 3 check, but TinyDB's own CI runs `mypy` and `pycodestyle`, not ruff. Checking with a different tool would pass code that the project CI then rejects, or the other way round.
- One Reviewer job holding both the agent and `pull-requests: write` meant an injected Reviewer shared a process tree with a write token. GitHub Models also stopped being used (ADR-012), so `models: read` was no longer needed.

## Decision

- Every agent command runs as a separate Linux user (`autose-agent`) through `sudo -n -u autose-agent env -i`, with an empty environment (only PATH, HOME, LANG and one Python setting). The working copy is handed to that user before a session and taken back after it (`sandbox.py`).
- The per-role allowlist stays (`guard.py`). `git`, network tools, `pip`, `env` and `/proc` are blocked for every role. Quoted text is not mistaken for a command (`~` inside quotes is allowed). Backticks and `$(...)` are blocked even inside double quotes, and the refusal tells the agent to write files with a quoted heredoc instead.
- Stage 3 runs `mypy` and `pycodestyle` exactly as the project CI does.
- Stage 6 is two jobs. `review-run` runs the Reviewer with `contents: read`, `issues: read`, `pull-requests: read` only. It always checks out the harness from `master`; the PR head is checked out into a separate folder as data. `review-post` runs no agent; it holds `pull-requests: write`, `issues: write` and `actions: write` to post the review and start the next round.
- The "never merge" rule is still enforced in code: no code path calls merge, and `master` is protected.

## Consequences

- Good: a hijacked agent cannot read secrets, the token or the runner's files, and cannot push. The Reviewer can never run code from the PR it is judging as part of its own harness.
- Good: a Stage 3 pass means the same as a green project CI run (every PR that reached Stage 5 had green CI).
- Bad: `sudo` and a second user make local runs need the same setup. When no sandbox user exists, `sandbox.py` falls back to running as the current user, so local self-tests do not cover the user switch.
- Bad: agents still try `git diff` or `git status` (14 of 72 runs had at least one blocked git command, see "blocked" in `stage_results.json`). Each attempt costs a step but is harmless.
