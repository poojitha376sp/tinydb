# ADR-009: Defense-in-Depth Against Prompt Injection, Loops, and Runaway Quotas (D9 — Safety and Failures)

## Status

Accepted. Amended by ADR-013 (test repair route) and ADR-015 (robust action parsing). (Proposed before any agent code was written; status set after the runs.)

## Context

Public GitHub issues and comments are untrusted user inputs capable of carrying prompt-injection payloads, while unguarded agent loops can stall on repetitive failing edits or exhaust daily free-tier API quotas.

## Decision

Enforce four layered safety and failure-handling controls:

- **Prompt & Shell Injection Containment:** Untrusted issue and comment strings are never interpolated into `${{ ... }}` expressions inside YAML `run:` blocks; instead, they are passed via `env:` variables into files and wrapped inside `<untrusted_issue>` XML tags with explicit system instructions to treat the contents strictly as untrusted data. Combined with credential stripping (ADR-005) and command/path allowlists, a hijacked agent cannot access secrets or modify workflows.
- **Stuck-Loop Detection:** In addition to hard caps (timeout-minutes per job, max agent steps per stage, max 3 Builder retries, max 2 review rounds, and a per-run token ceiling calibrated after the first baseline run), if Stage 4b produces the exact same test failure twice in a row, the orchestrator aborts the local retry loop and routes backward to Stage 2 (Design) rather than wasting a third identical attempt.
- **Zero-Spend Hard Ceiling:** Operating exclusively on free-tier keys without an attached billing account enforces a strict $0.00 financial ceiling, paired with exponential backoff for rate limits.
- **Deterministic Failure Halting:** When any stage exhausts its retries or fails a gate check, the orchestrator records the diagnostic failure reason in that stage's artifact, updates the issue status comment to stopped, applies the autose-failed label, and exits cleanly without opening a PR.

## Alternatives considered

- **Relying solely on prompt-level instructions ("ignore malicious instructions"):** Rejected because prompt instructions alone are insufficient against adversarial inputs without shell-env isolation and token stripping.
- **Allowing all 3 Builder retries even on identical errors:** Rejected because repeating identical failing edits wastes free-tier quota and degrades context quality (as documented in the SWEnergy findings).

## Consequences

- **Good:** Protects repository integrity and API quotas against malicious issues and infinite retry loops while ensuring transparent failure reporting on GitHub.
- **Bad:** Hard step and retry caps may prematurely halt legitimate but unusually complex multi-file issues if free-tier rate limits coincide with heavy debugging loops.
