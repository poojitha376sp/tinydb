# ADR-001: Four-Agent Role Partitioning with Deterministic Glue (D1 — Splitting the Work)

## Status

Accepted. (Proposed before any agent code was written; status set after the runs.)

## Context

An automated workflow turning GitHub issues into reviewed pull requests spans six distinct stages—Requirements, Design, Implementation, Testing, Release, and Review—each carrying different cognitive demands and information-isolation requirements. Combining every stage into a single agent creates context saturation and allows the code generator to grade its own work. Conversely, assigning a dedicated LLM agent to every single stage multiplies hand-offs, amplifies inter-agent miscommunication, and inflates token consumption.

## Decision

Partition the system into four specialized LLM agents—Analyst (Stages 1 and 2: Requirements and Design), Test Author (Stage 4a: writing acceptance tests before implementation), Builder (Stages 3 and 4b: implementing changes and fixing failing tests), and Reviewer (Stage 6: independent code review)—while executing Stage 5 (Release) and every stage validation gate in deterministic Python code. Agent boundaries are drawn strictly where one role must be prevented from seeing another's output: the Test Author cannot see the Builder's code or reasoning, the Builder cannot see the test source code (receiving only failing test names and error messages), and the Reviewer cannot see spec.md, design.md, or any prior agent's conversation.

## Alternatives considered

- **Single monolithic agent:** Rejected because a single context window degrades over long multi-stage trajectories and violates reviewer independence by letting the author evaluate its own changes.
- **Six agents (one per stage):** Rejected because splitting Requirements from Design adds an unnecessary hand-off without an information barrier, while using LLMs for deterministic GitHub release operations wastes quota and introduces non-determinism. Empirical findings (the MAST multi-agent failure study) attribute 32% of multi-agent failures to inter-agent misunderstanding, with multi-agent architectures consuming roughly 15 times more tokens than leaner designs.

## Consequences

- **Good:** Preserves high cohesion between requirements and design in the Analyst while enforcing strict blind spots between test authoring, implementation, and review. Keeps deterministic "executor" work (git operations, linting, test running, PR creation) fast, predictable, and free of token cost.
- **Bad:** Splitting Stage 4 into an LLM Test Author (4a) and a deterministic test runner (4b) adds an extra artifact boundary (spec.md $\rightarrow$ test files) that must remain strictly synchronized with the Analyst's acceptance criteria IDs.
