# ADR-007: Deterministic-First Gate Checks with Explicit CI Triggering (D7 — Checks)

## Status

Proposed

## Context

Each of the six SDLC stages must pass an objective verification gate before advancing, or halt and record the failure reason in its artifact. Relying on LLM self-certification leads to false positives ("rubber-stamping"), and in Stage 5, a pull request opened using GitHub Actions' default GITHUB_TOKEN will not automatically trigger pull_request CI workflows due to GitHub's recursive-run prevention—meaning passive polling of PR status checks would hang indefinitely.

## Decision

Enforce deterministic and grounding checks executed by the Python orchestrator at every stage, reserving LLM judgment strictly for Stage 6 review synthesis:

- **Stage 1 (spec.md):** Deterministic parser verifying every Acceptance Criterion (AC) has a unique ID, follows the A1 skill's EARS-style `SHALL ... when/if` syntax, and contains zero banned ambiguous words.
- **Stage 2 (design.md):** Grounding check verifying via AST/filesystem inspection that every referenced file and function exists in the base commit (or is explicitly tagged NEW).
- **Stage 3 (diff.patch):** Deterministic check verifying clean compilation, `import tinydb` success, ruff and mypy zero-error exit codes, and compliance with the planned file allowlist.
- **Stage 4 (test_report.md):** Deterministic Red-Green check verifying that every new test fails on the unpatched base commit and passes on the Builder's branch, every AC ID maps to at least one test name, and the full existing test suite passes.
- **Stage 5 (pr.md):** After opening the PR, the orchestrator explicitly triggers the repository's CI workflow via workflow_dispatch on the PR branch commit and polls that run until it reports success. This requires adding a `workflow_dispatch:` trigger to tinydb's `ci-workflow.yml`, which today starts only on `push` and `pull_request`; a branch push made with GITHUB_TOKEN does not start CI either, for the same recursive-run reason.
- **Stage 6 (review.md):** Grounding and schema check verifying valid JSON output and confirming every review finding cites a real file:line and an executed shell command with its captured output.

## Alternatives considered

- **LLM-as-a-Judge gates at every stage:** Rejected because LLM judges consume extra quota, add latency, and frequently approve malformed specs or hallucinated symbol names.
- **Passively waiting for statusCheckRollup in Stage 5:** Rejected because PRs created by GITHUB_TOKEN suppress `on: pull_request` CI triggers, causing an infinite wait.

## Consequences

- **Good:** Guarantees that no stage advances on hallucinated symbols, unverified tests, or unexecuted CI. Explicitly triggering CI via workflow_dispatch eliminates GITHUB_TOKEN event-suppression deadlocks.
- **Bad:** Requiring every new test to fail on the base commit (Red-Green) means pure refactoring issues without observable behavior changes must include at least one structural/regression assertion that fails pre-change.

## Lectures

Lecture 4 & 5 (EARS-style requirements and spec-derived testing), Lecture 7 (five levels of verification, ordered cheapest/deterministic first), and Lecture 10 ("the agent can't say it's done; the build has to").
