# ADR-010: Triage-Gated Triggers and Per-Issue Concurrency Queuing (D10 — Triggers)

## Status

Superseded by ADR-017. (Proposed before any agent code was written; status set after the runs.)

## Context

Triggering agent workflows automatically on every newly opened issue exposes the repository's free-tier quota to spam, while overlapping triggers (e.g., adding the autose label and posting /autose simultaneously) can cause git branch collisions and corrupted status comments. Furthermore, on `issues: [labeled]` events, GitHub sets `issue.author_association` to the issue author's role rather than the labeler's role—checking it would falsely reject a maintainer who labels an external user's bug report.

## Decision

- **Authorized Trigger Events:** Start the workflow only on `issues: [labeled]` where `github.event.label.name == 'autose'`, or `issue_comment: [created]` where `github.event.comment.body` starts with `/autose`.
- **Role Verification:**
  - Label trigger: Verify `github.event.sender.type == 'User'`. Because GitHub natively restricts applying labels to users with at least Triage repository permissions, no author_association check is performed on the issue object.
  - Comment trigger: Verify `github.event.sender.type == 'User'`, ignore comments posted by the workflow bot itself, and require `github.event.comment.author_association` $\in$ {'OWNER', 'MEMBER', 'COLLABORATOR'}.
- **Per-Issue Concurrency Queue:** Configure workflow-level concurrency grouping by issue number:

```yaml
concurrency:
  group: autose-${{ github.event.issue.number }}
  cancel-in-progress: false
```

This allows different issues to run in parallel while queuing duplicate triggers on the same issue without killing an active run mid-commit. GitHub keeps at most one pending run per concurrency group, so if a third trigger arrives while one run is active and one is pending, the older pending run is cancelled and the newest one waits instead.

## Alternatives considered

- **Triggering on `issues: [opened]` or allowing any commenter to run /autose:** Rejected because any external user could spam issues/comments and exhaust the free-tier API quota.
- **Checking `github.event.issue.author_association` on label events:** Rejected because it inspects the issue opener rather than the maintainer applying the label, blocking valid triage workflows.

## Consequences

- **Good:** Allows maintainers to safely trigger AutoSE on community-submitted issues via labeling, prevents unauthorized quota drain, and avoids race conditions on shared branches and status comments.
- **Bad:** External contributors cannot self-invoke the workflow without a collaborator or maintainer applying the label or /autose command.
