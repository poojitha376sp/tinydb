# ADR-013: A Wrong Acceptance Test Gets One Repair Before Design Is Blamed (amends ADR-002 and ADR-009)

## Status

Accepted. Amends ADR-002 (control flow) and ADR-009 (stuck-loop rule).

## Context

ADR-002 and ADR-009 assume that when Stage 4b fails the same way twice, the plan is wrong, so the run goes back to Stage 2 (Design). Issue I3 (#10) showed a different cause: the acceptance test itself was wrong, twice, in two different ways.

- Run 44790279547: the tests used `TinyDB(':memory:')`. TinyDB has no in-memory path; this writes a real file named `:memory:` that every test shares, so one test saw another's tables.
- Run 44819950934: a test called `table.get(doc_id)`. The first positional parameter of `get` is a query, so the call never looked up the ID.

The Builder could not fix either test, because it cannot see or change tests (ADR-003), and a new design could not fix them either. Both runs stopped at Stage 4b after three Builder attempts, although their code passed all hidden tests (4/4).

## Decision

The known mistake is rejected at the red check: a test file that uses `TinyDB(':memory:')` fails Stage 4a with a message to use `MemoryStorage` or `tmp_path`, and the Test Author prompt says the same.

For mistakes nobody has listed yet: when Stage 4b fails with the same failure signature twice in a row and the code builds, the orchestrator first gives the Test Author **one** repair turn (`MAX_TEST_REPAIRS = 1`) before escalating to Design:

- The Test Author sees the spec, its own tests, and only the failure messages (`failure.md`), never the Builder's code or diff.
- The repaired tests must still fail on the base commit (the red check of ADR-007 runs again).
- The run records stage `4a-test-repair` and keeps the old tests as `tests_before_repair.py`, so the change is visible.
- If the same failure continues after the repair, the ADR-002 route (back to Design once, then stop) applies unchanged.

## Consequences

- Good: I3's third run (44874308479) used `MemoryStorage`, passed every stage at the first attempt and opened PR #19, which passed all hidden tests and was approved by the Reviewer. That success came from the `:memory:` rule, not from the repair turn.
- Honest limit: no real run has needed the repair turn yet (no run records `4a-test-repair`). It is covered only by a scripted self-test (`check_pipeline.py`, wrong-test repair), so its real-world effect is unmeasured.
- Good: information hiding is kept: the Test Author still never sees the implementation.
- Bad: a weak Test Author could "repair" a correct test into a weaker one. The red-on-base check limits this (a test that passes on the old code is rejected), and the Reviewer still checks the change against the issue.
