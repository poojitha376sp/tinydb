# ADR-005: Credential-Stripped Agents and Deterministic GitHub Gateway (D5 — Tools)

## Status

Proposed

## Context

Giving LLM agents direct GitHub API tokens or unrestricted shell access creates severe blast-radius risks: a prompt-injected issue could exfiltrate secrets, alter .github/workflows/, delete failing tests to fake a green build, or merge its own pull request.

## Decision

Enforce strict credential and capability separation so that no LLM agent ever holds a GITHUB_TOKEN or communicates with GitHub directly:

- Repository checkout runs with `persist-credentials: false`, and GITHUB_TOKEN is unset from every agent subprocess environment. Only the plain-Python Orchestrator and Release script invoke `gh` CLI commands using the job's scoped token.
- **Analyst:** Read-only file inspection (read, grep, list_files).
- **Test Author:** Read access, write access restricted strictly to new test files, and pytest execution.
- **Builder:** Read access, write access restricted to tinydb/ (the target package), and a strict command allowlist. Because mini-swe-agent reads and edits files through shell commands, the allowlist covers the file commands it needs (cat, ls, grep, sed, python) plus pytest, ruff and mypy; everything else is blocked. After every Builder turn, a deterministic path check rejects and reverts any modification to .github/, existing test files, or packaging/setup files.
- **Reviewer:** Runs in a separate job with `contents: read` permissions and unrestricted read/execution inside a throwaway workspace copy. The review job's plain-Python code (not the Reviewer agent) additionally holds `pull-requests: write` (post review.md), `issues: write` (update the status comment), `actions: write` (start the next round via workflow_dispatch, ADR-002) and `models: read` (call GitHub Models, ADR-006). The job has no `contents: write`, so nothing in it can push.
- **Explicit security boundary:** Because repository branch protection on master requires a PR without mandatory human approval counts, the Orchestrator's GITHUB_TOKEN technically possesses API capability to merge a PR; the "never merge" invariant is therefore enforced deterministically in Python code (which contains no merge call) rather than by branch-protection permissions alone.

## Alternatives considered

- **Connecting agents to the GitHub MCP server:** Rejected because agents do not need direct GitHub access when the orchestrator handles GitHub I/O, and MCP introduces unnecessary attack surface via tool-level prompt injection and static token exposure.
- **Unrestricted bash tool for the Builder:** Rejected because an unrestricted shell allows the agent to inspect environment variables, alter git hooks, or modify existing tests to force a pass.

## Consequences

- **Good:** Eliminates token exfiltration and test-tampering exploits, prevents agents from mutating workflow definitions, and clearly documents the residual trust boundary around GITHUB_TOKEN merge capability.
- **Bad:** Strict file-path allowlists require updating the orchestrator configuration if a valid issue legitimately requires modifying top-level configuration or documentation files outside tinydb/.
